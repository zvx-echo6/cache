# C.A.C.H.E. — Crisis Assistant for Contingencies, Hardship & Emergencies

An offline survival and preparedness assistant for phones and computers. Everything runs on the device with no network: a local LLM, a library, Kiwix, maps and routing.

Cache is a framework. No data and no models ship inside the app: people add the sources they want (models, ZIMs, libraries, region packs). The app must never depend on hosting run by the owner, so it can go to the app stores later.

Cache is built to pull data while online and then work offline for long periods, until it can get back online. Data with a clear end date, such as weather forecasts and alerts, carries the time it was fetched and when it stops being valid. Once it has expired, the app and the assistant say so plainly (for example: "I no longer have weather data. We need to go online for more.") instead of using it, and the app refreshes it when a connection returns.

Cache aims to be an all-in-one emergency app: install it, configure it while things are normal, and not find out in a crisis that some other app should have been installed beforehand.

| Library | Libraries are vector databases, used as they are: Qdrant collections, opened inside the app by Qdrant Edge (Qdrant's embedded engine, Apache-2.0, in beta). No server, no conversion, no splitting. A library is added from a Qdrant server (address, collection name, optional API key; the app downloads a snapshot of the collection), from a download link, or from a file on the device or SD card. A library comes with a small settings file next to the database, written by whoever builds it: which payload fields hold the title, text, page, source type and link; which points to leave out of search (for example points flagged as junk or replaced); and the embedding model the collection was built with (a GGUF run by llama.cpp), so queries match its vectors. Cache reads it when the library is added and asks nothing. Without a settings file, Cache guesses from common field names and the vector size, and asks only what it can't work out. An Advanced section on the add-library screen shows the same settings, filled in, to change: field mapping, leave-out rules, embedding model, keyword index on or off, and the Qdrant server to update from. Each point's payload decides what its citation shows and opens: for example a transcript point opens its video at the cited time, and a point taken from a ZIM opens that ZIM's article when the ZIM is on the device. A library bigger than the phone's memory must still open, with vectors and indexes read from storage. The app ships no library. The recon code is to be published on GitHub so people can build their own libraries; this is a to-do before any public release and needs the owner's go. Decided 2026-10-25. |
| Updates | Every source has an update action; what it does depends on where the source came from. Qdrant server: the app sends the collection's segment manifest and downloads only the changed segments (Qdrant partial snapshots). Download link: the app checks whether the file is newer and downloads it whole. Catalogue ZIM: the app checks the catalogue for a newer dated release of the same title and downloads it whole, then uses a ready-made index if one is offered or rebuilds the ZIM's keyword index on the device. Imported file: Replace, choosing the newer file. The old copy stays in use until the new one is downloaded and checked, and the app checks free space first (an update can briefly need room for both). Citations keep working across updates; one whose item is gone says so. Update settings, with defaults for everything and an override per source: how often (off, daily, weekly, monthly), notify only or download automatically, ask before downloads over a set size, Wi-Fi only, only while charging, quiet hours, and Update all now. Android runs scheduled updates within these conditions; iOS runs background work when the system allows (usually overnight while charging), so a schedule there is approximate. Weather and alerts refresh through the same scheduler with their own intervals. Decided 2026-10-25. |

Map fonts ship with the app. Simple: "Download a region". Advanced: add or edit layer definitions and every source address by hand, which is how a user points Cache at their own server. A layer or service that needs a connection says so instead of disappearing. Decided 2026-10-25. |

## Cache 1.0

Everything in this plan stays in it, but the work is ordered so a usable app reaches the family's phones first. Cache 1.0 is the line; everything else is labelled 1.x and comes after. Decided 2026-10-25. PeerTube moved into 1.0 on 2026-10-25 at the owner's request.

## Build order

Each step ends with something usable on a phone. Riskiest first. Updated 2026-10-24.

1. **Chat on the phone.** Flutter app with a chat screen running uncensored E2B in llama.cpp, fully offline. Proves the model on the Pixel 8 and the iPhone 15 Pro Max. Built inside the app shell from the mockups (four tabs; tabs other than Ask are placeholders). It includes the tool loop and citation check: the model calls a search tool, results come back tagged with numbered IDs, the model cites them, and the app shows only citations that match a real result (others are dropped and the answer is marked as not from your sources). Citations always open local content: each result's ID maps to its local address (ZIM article, library page, map point), and the model never writes the links. A small test-only search tool with test data proves this; nothing ships with it. The chat engine has a pluggable model backend (llama.cpp now, remote connectors later) so the tool loop and citations work the same with either. Code and builds on the owner's desktop in `C:\src\cache`.
2. **Library.** Open a library (Qdrant collection) through Qdrant Edge: add it from a Qdrant server, a link or a file; read the library's settings file (field mapping, leave-out rules, embedding model as a GGUF in llama.cpp), with the Advanced section to change them; answers cite from each point's payload. Proven first with a small collection, then with one bigger than the phone's memory. Updates (partial snapshots from a Qdrant server, newer files from links, Replace for imported files) and the update settings and scheduler are built here and reused by every later source.
3. **Browse.** The offline browser: ZIMs open like websites and library items open as pages. Kiwix's public catalogue (showing mini, no-pictures and full variants with sizes), added catalogues (OPDS), import from a file; start page, tabs, bookmarks, history. Web links the model writes (for example Wikipedia URLs) open the local ZIM copy when one exists, otherwise they are marked not available offline.
4. **Search.** One search box: Tantivy (Rust) keyword indexes built on the device for ZIMs and for libraries (from the mapped text field, unless the library has a scored full-text index of its own), merged with meaning search through Qdrant Edge in the same Rust core. Background indexing on the device; ready-made indexes for large ZIMs published with the region packs.
5. **Model library.** Hugging Face search and download inside the app, with size and RAM fit. Cached models (the owner's trained models) listed at the top. Also the optional network model connector (OpenAI-compatible, local Wi-Fi or internet; mDNS discovery or IP address and port), picked here as on-device or network. Tool check for every model (on-device and network); only models that pass can be used.
6. **The assistant's brain.** Train E2B on a C.A.C.H.E. version of the AIDA course (same tool use, complete answers), quiz it, then wire its tools to the library, Kiwix and search. Then E4B, 12B, and last Qwen (needs the course converted to ChatML). Published on Hugging Face as Cached models. Training captures wait until every tool exists in the app's own code (search, read, navigate including off-road, nearby, locate, live_data, web_search), so the model learns exactly what the app returns.
7. **Region packs.** The build pipeline from public open data (see Map data sources) and publishing to Hugging Face datasets. Baseline regions chosen by the owner.
8. **Live sources.** The on-device source engine (definition files, fetch once and share, coalescing, quotas, secure key storage, validity and expiry, scheduled refresh when online, field mapping), the starter emergency catalogue, Home status cards for live data, and the `live_data` tool with the weather source (cached Open-Meteo forecasts per place, with their age) and the alerts source. Alert matching against location and saved places, notifications, and "Ask about this alert".
9. **Maps.** Offline maps from region packs at full navi parity: basemap, hillshade and terrain, land cover, land ownership, places, geocoder, nearby (MapLibre + PMTiles). Coordinates: lat/long, USNG/MGRS and Plus Codes offline; what3words online with cached words for saved places. Imported repeater lists on the map and in nearby.
10. **Routing and navigation.** Valhalla road routing on the device (Valhalla 3.7.0 behind a small C shim in the core); navi's off-road Auto search ported to Rust, with the region pack builder and parity tests against navi; then turn-by-turn navigation from the phone's GPS (progress, spoken prompts, off-route recalculation, background service). Off-road and navigate results feed the assistant's navigate tool, and they are built before the training captures.
11. **iPhone.** Same app on iOS, built and sent to TestFlight by a GitHub Actions macOS workflow.
12. **Videos.** PeerTube connector (official API, login), browse and search an instance, streaming, offline downloads with resolution choice, offline player, optional YouTube connector (online only: search, play, bookmark; user's own API key with in-app setup instructions), citations of transcript points that open the video at the cited time.

## Size and compression

- Measure each layer's size per region in step 7 and choose compression per layer; show sizes per layer in the download screen.
- Terrain: LERC within about 1 m of error, 30 m resolution, fewer tiles over flat ground.
- Land cover: 30 m for off-road routing, run-length or zstd compression.
- Basemap: build to zoom 14 and overzoom beyond it; drop fields the app never shows.
- Places: only the columns the app uses, columnar with zstd.
- Valhalla: leave out transit and other unused data.
- ZIMs: offer the mini, no-pictures and full variants with their sizes.
- Libraries: used as they are. Any compression (for example Qdrant's own vector quantization) is set by whoever builds the collection.
- Tantivy: no word positions on fields that never need phrase search.
- Large files (ZIMs, libraries, region packs) can live on an SD card where the phone has one.
- Videos: download at a chosen resolution or audio only; show the size before downloading.

## Known facts from testing

- Gemma 4 E2B, E4B and both E2B uncensored variants train cleanly on the AIDA course with the box's pinned env (2026-10-21): same token ids as the 12B tokenizer, assistant-only masking correct, llama.cpp converts to Q6_K. On one H100: E2B about 2.35 h, E4B about 2.7 h for 881 steps. Prep files: `/mnt/mesh-train/export/aida-training-candidates-20261020-v25b/small-gemma-prep/`.
- Gradient offload is hard-coded in the trainer (`train_gemma_trajectory.py:465`, `use_gradient_checkpointing='unsloth'`); worth testing off on a machine with spare GPU memory.
- Trained Josiefied Qwen3 8B models exist (`mesh-8b-tuned` r1-r3), but on the older passages course, not the current tool course.
- Stock E2B on an iPhone (PocketPal, 2048 context): a well-organised answer with confident factual slips. Library grounding is the fix.
- The owner's desktop (2026-10-24): Windows 11 Pro, Ryzen 7 3700X, 64 GB RAM. Flutter 3.44.8, Android Studio 2026.2.1, Android SDK 37, NDK 28.2, CMake 3.22; `flutter doctor` clean; emulator acceleration (WHPX) works.
